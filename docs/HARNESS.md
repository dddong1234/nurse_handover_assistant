# Nurse Handover Assistant 하네스 설계

## 1. 목적

이 하네스는 여러 AI 에이전트가 UI와 핵심 로직을 나누어 구현하더라도 프로젝트의 제품 목표, 임상 안전 경계, 파일 소유권과 검증 절차에서 이탈하지 않도록 한다.

하네스 자체도 포트폴리오 산출물이다. 단순히 AI가 코드를 생성했다는 사실이 아니라, 작업을 분해하고 제약하고 검증하며 결정 근거를 축적하는 능력을 보여준다.

## 3. 적용 구조

```text
AGENTS.md                         공통 지시와 역할·품질 게이트
├─ services/AGENTS.md            핵심 로직 계층 규칙
├─ tests/AGENTS.md               테스트 작성 규칙
├─ scripts/check_harness.py      아키텍처·문서·구조 드리프트 센서
├─ tests/test_harness_checks.py  센서 자체의 회귀 테스트
├─ .github/workflows/harness.yml push/PR/주기적 자동 검사
└─ docs/
   ├─ decisions/                 결정과 이유
   ├─ conventions/               작업·버전·검증 관례
   ├─ domain/                    간호 인수인계 용어와 흐름
   ├─ failures/                  실패와 재시도 금지 근거
   └─ AGENT_WORKLOG.md           위임·검증·수정 감사 기록
```

## 4. 구성요소별 적용과 결정 근거

### 4.1 지시 문서

적용:

- 루트 `AGENTS.md`에 목표, 우선순위, 역할, 금지사항과 품질 게이트를 둔다.
- `services/`와 `tests/`에 더 구체적인 하위 지시 문서를 둔다.
- 에이전트는 작업 시작 시 하네스 버전과 소유 파일을 명시적으로 수용한다.

근거:

- 공통 규칙과 로직·테스트 규칙을 분리하면 루트 문서를 짧게 유지하면서 현재 작업에 필요한 규칙을 가까운 위치에서 제공할 수 있다.
- 시작 수용 메시지는 에이전트가 역할과 금지 범위를 읽었는지 감독자가 확인할 수 있는 최소 증거다.

### 4.2 아키텍처 제약

적용:

- `scripts/check_harness.py`가 `services/`에서 `streamlit`과 `app` import를 차단한다.
- 프런트엔드와 핵심 로직의 파일 소유권을 분리한다.
- 병렬 에이전트가 같은 파일을 수정해야 하면 작업을 직렬화한다.

근거:

- 현재 프로젝트의 가장 중요한 구조적 경계는 UI와 deterministic 임상 로직의 분리다.
- 초기 포트폴리오 단계에서 별도 import-linter 의존성을 추가하는 대신 Python 표준 라이브러리 AST 검사로 빠르고 재현 가능한 제약을 제공한다.
- 프로젝트가 패키지 구조로 확장되면 import-linter 또는 Ruff 규칙으로 강화할 수 있다.

### 4.3 피드백 루프

가이드:

- 승인된 Figma, 구조화된 UI 데이터 계약, 디렉터리별 `AGENTS.md`, 테스트 사례

센서:

- 단위 테스트
- `scripts/check_harness.py`
- GitHub Actions의 push, pull request, 주기 검사
- 큰 기능마다 수행하는 감독 에이전트의 코드·화면 검증

근거:

- 문서만으로는 이탈을 막을 수 없으므로 작업 전 가이드와 작업 후 자동 센서를 함께 둔다.
- 첫 실패는 담당 에이전트가 수정하고 두 번째 검증에도 중대한 문제가 남으면 사용자에게 알리는 규칙은 사용자가 지정한 감독 방식을 그대로 구현한다.

### 4.4 지식 저장소

적용:

- `docs/decisions/`: 기술·제품 결정과 포기한 대안
- `docs/conventions/`: 버전, 위임, 테스트, 검증 방식
- `docs/domain/`: 간호 인수인계의 용어와 업무 흐름
- `docs/failures/`: 실패 원인과 같은 접근을 반복하지 않기 위한 지침
- `docs/AGENT_WORKLOG.md`: 실제 위임과 검증 증거

근거:

- 에이전트는 새 세션마다 이전 결정의 이유를 자동으로 알지 못한다.
- 특히 임상 용어와 실패 기록이 없으면 데이터 의미를 바꾸거나 이미 실패한 접근을 반복할 위험이 있다.

### 4.5 가비지 컬렉션

적용:

- 필수 하네스 문서 누락 감지
- `VERSION`의 SemVer 형식과 `CHANGELOG.md` 동기화 검사
- 임시 파일명과 구조 드리프트 감지
- 서비스 계층의 UI 의존 감지
- CI에서 매주 및 코드 변경 시 반복 실행

근거:

- 드리프트는 코드, 문서, 디렉터리 구조에서 각각 발생하므로 세 범주를 모두 검사한다.
- 자동 삭제는 기존 사용자 파일을 손상할 수 있으므로 센서는 실패만 보고하고, 정리는 감독 에이전트가 정확한 대상을 확인한 뒤 수행한다.

## 5. 실행 방법

```powershell
python scripts/check_harness.py --root .
python -m unittest discover -s tests -v
```

성공 기준:

- 하네스 검사가 `HARNESS CHECK PASSED`를 출력하고 종료 코드 `0`을 반환한다.
- 모든 단위 테스트가 통과한다.
- `docs/AGENT_WORKLOG.md`에 해당 작업의 감독 검증 근거가 기록된다.

## 6. 버전 관리

### 프로젝트 버전

`VERSION`을 단일 기준으로 사용하는 SemVer 방식이다.

- `MAJOR`: 호환되지 않는 제품 방향 또는 데이터 계약 변경
- `MINOR`: 주요 화면, 비교 엔진, AI 요약 등 사용자 기능 추가
- `PATCH`: 기존 계약을 유지하는 수정과 품질 개선
- 개발 버전: `X.Y.Z-dev.N`

예정 마일스톤:

| 버전 | 의미 |
|---|---|
| `0.3.x` | 기존 Streamlit MVP 기준선과 하네스 도입 |
| `0.4.x` | 구조화된 차이 비교 엔진 |
| `0.5.x` | Figma 기반 UI 통합 |
| `0.6.x` | 근거 제한 OpenAI 요약 |
| `1.0.0` | 검증된 포트폴리오 시연 안정판 |

### 하네스 버전

하네스는 `AGENTS.md`의 `Harness-Version`으로 별도 관리한다.

- 역할, 품질 게이트, 보안 경계가 바뀌면 하네스 `MINOR` 이상을 올린다.
- 오탈자나 의미 없는 설명 정리는 `PATCH`를 올린다.
- 모든 서브에이전트 작업 기록에는 사용한 하네스 버전을 남긴다.

### Git 통제

- 서브에이전트는 Git 상태를 변경하지 않는다.
- 감독 검증을 통과한 결과만 커밋·태그 후보가 된다.
- 사용자 소유의 미추적 변경은 별도 범위로 유지한다.
- 릴리스 태그는 검증된 안정 버전에만 `vX.Y.Z` 형식으로 생성한다.

## 7. 현재 한계와 강화 시점

- 현재 센서는 서비스 계층과 문서·구조 드리프트에 집중한다.
- Figma 구현이 시작되면 UI 상태별 시각 회귀 검증을 추가한다.
- 비교 엔진이 구조화되면 임상 중요도별 누락·오탐 테스트를 추가한다.
- OpenAI 기능이 추가되면 근거 이탈, fallback, timeout, 구조화 출력 검증을 추가한다.
- 실제 EMR 연동을 검토할 때는 권한, 감사로그, 데이터 반출과 인증 요구를 별도 하네스로 확장한다.

## 8. Vercel 배포 경계

최종 포트폴리오 배포 대상은 Vercel이다. 이에 따라 하네스는 다음 구조적 경계를 강제한다.

- 프런트엔드는 Figma를 기준으로 Next.js에서 구현한다.
- 기존 Python 비교 엔진은 UI에서 분리하고 FastAPI Vercel Function으로 노출한다.
- Streamlit 앱은 기존 동작의 기준선으로 유지하되 최종 Vercel UI로 확장하지 않는다.
- JSON 데모 파일은 읽기 전용 fixture로만 사용한다.
- 사용자 편집 상태는 1차 배포에서 브라우저 세션에 한정한다.
- OpenAI 키와 호출은 서버 함수에만 둔다.
- 공유 영속성이 필요할 때만 Postgres 등 외부 저장소를 별도 결정한다.

이 경계는 Vercel Functions가 로컬 개발환경과 같은 영속 파일시스템을 제공하지 않고, 파일 쓰기에는 별도 객체 저장소 또는 데이터베이스가 필요하기 때문에 채택했다. 자세한 근거는 `docs/decisions/002-vercel-deployment-target.md`에 기록한다.
