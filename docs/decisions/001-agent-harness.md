# ADR-001: 저장소 기반 에이전트 하네스 도입

## 상태

확정 — 2026-08-27

## 배경

프런트엔드와 핵심 로직을 서로 다른 AI 에이전트가 구현하고 감독 에이전트가 통합한다. 역할과 검증 절차가 프롬프트에만 존재하면 세션이 바뀌거나 작업이 길어질 때 목표, 파일 경계와 안전 규칙이 흐려질 수 있다.

## 결정

다음 다섯 요소를 저장소에 함께 둔다.

1. 루트와 디렉터리별 `AGENTS.md`
2. 표준 라이브러리 기반 아키텍처·드리프트 검사
3. 테스트와 CI 및 감독 품질 게이트
4. 결정·도메인·실패·작업 기록용 `docs/` 구조
5. 자동 삭제 없는 드리프트 탐지형 가비지 컬렉션

프로젝트 버전과 하네스 버전은 분리한다. 서브에이전트는 Git을 변경하지 않는다.

## 이유

- 규칙을 저장소에 두면 모든 작업자가 같은 기준을 반복해서 읽을 수 있다.
- 실행 가능한 센서가 문서만으로 발견하기 어려운 구조 위반과 드리프트를 차단한다.
- UI와 임상 로직을 분리하면 병렬 작업 충돌과 안전 경계 훼손 가능성이 줄어든다.
- 결정과 실패 이유를 기록하면 이후 에이전트가 같은 논의를 반복하지 않는다.
- 자동 삭제를 피하면 기존 미추적 파일과 사용자 작업을 보호할 수 있다.

## 포기한 대안

### 에이전트 프롬프트만 사용

세션 간 지속성과 자동 검증이 없어 제외했다.

### 즉시 Ruff, mypy, import-linter 전체 도입

현재 코드 규모에 비해 초기 설정과 의존성 비용이 크다. 우선 표준 라이브러리 AST 센서를 사용하고 패키지 구조가 확대되면 재검토한다.

### 드리프트 파일 자동 삭제

사용자 파일을 잘못 삭제할 위험이 있어 제외했다. 탐지 후 감독 검토 방식을 사용한다.

## 결과

- 구현 에이전트는 시작과 종료 시 정해진 계약을 보고해야 한다.
- 큰 기능은 감독 검증을 통과해야 다음 단계로 이동한다.
- 하네스 문서, 구조 또는 버전 불일치는 자동 검사 실패로 나타난다.
- 하네스 변경 자체도 버전과 작업 기록의 대상이 된다.
