# 인수인계·차팅 통합 EMR 작업공간 — 공동 설계안

기준일: 2026-09-23
상태: 두 프로젝트 담당 에이전트의 1차 기술 협의 반영. 기존 Figma 원본 재열람 완료. 새 통합 시안·제품 통합 구현·사용자 검증은 아직 수행하지 않음. 사용자 승인된 최종 아키텍처가 아닌 공동 검토안.
작업 범위: 사용자의 “EMR 에이전트랑 대화나누면서 둘이 합쳐봐” 요청에 따른 통합 구조와 구현 접점 구체화.
적용 하네스: 인수인계 1.2.0 및 차팅 저장소의 기존 제품 불변 조건.

## 1. 사용자 의도와 승인 범위

- 하나의 실제 EMR 서비스를 사용하는 듯한 일관된 작업 경험을 만든다.
- 인수인계와 차팅을 함께 소개하는 랜딩페이지는 후속 단계다.
- 인수인계 첫 화면은 선택 환자의 이번 근무 확인 사항에 집중한다.
- 기존 화면의 약한 시각 위계, 반복 정보, 무엇부터 볼지 불명확한 문제를 개선한다.
- 간호사 1인의 의견에서 얻은 5개 임상 영역은 유지한다. 이 의견은 화면 배치의 사용성 검증을 뜻하지 않는다.
- 합성 데이터 프로토타입이며 실제 운영 EMR 연동, 인증, 공유 영구저장, 처치·보고 자동 완료를 이번 조율로 도입하지 않는다.

## 3. 제안하는 통합 구조

최신 인수인계 Next 앱을 통합 호스트 후보로 삼는 데 양쪽 담당이 기술적으로 동의했다. 이미 날짜 단위 비교, 환자 기록, Python 서버 경로가 있고 차팅의 React 편집기와 프레임워크 독립 도메인 로직을 가져올 수 있기 때문이다. 최종 착수 기준은 새 통합 설계와 구현 계획 검토 후 고정한다.

```text
공통 작업공간
├─ 담당 환자 선택 / 환자 문맥 / 근무 정보
├─ 인수인계
│  ├─ 이번 근무 예정 · 새 결과 · 기록된 전달 요청
│  ├─ 결과 대기 · 최근 변화
│  └─ 이전·현재 비교와 원본 출처
├─ 환자 기록
│  └─ 현재 기록과 시간순 기록 조회
└─ 간호기록
   ├─ 하나의 SOAP 편집기
   ├─ 추천 채택 · 직접 수정 · 명시적 기록 추가
   └─ 선택한 추천/기록의 근거와 기록 전 확인
```

이는 정보 구조 제안이다. 시각 배치·크기·색상·반응형은 새 통합 Figma 검토 후 확정한다. 같은 Figma 파일 `KpybGW6Y8u9TyPSv61OcM9`, node `39:3`을 양쪽 기존 설계가 참조하며, 2026-09-23 인수인계 감독이 MCP screenshot으로 1440×1024 원본을 재열람했다. 환자 레일·문맥 헤더·중앙 편집·우측 근거의 공간 문법을 확인했다. 원본의 실시간 연결, 서명, 알레르기 안전성 대조, MAR 등은 통합에 새로 도입할 기능의 근거로 삼지 않는다. 기존 원본 재열람을 새로운 통합 화면 검증과 혼동하지 않는다.

공통 환자 목록은 한 번만 렌더링한다. 환자 선택의 소유자는 shell이며 모듈이 독립적으로 다른 환자를 선택하지 않는다. 우측 상세 영역은 현재 선택한 항목의 출처 또는 차팅 보조 정보를 제공하고 전체 항목 목록을 반복하지 않는다.

5개 임상 영역은 분류·필터와 전체 검토에 유지한다. 이번 근무 관련 업무 상태를 먼저 보여주는 것은 정보 배치의 변경이며 임상 위험도 판단이 아니다. 데이터 부족과 기준 기록 부재는 “할 일 없음”과 구분한다.

## 4. 연결 계약 제안

| 공통 필드 | 의미와 규칙 |
|---|---|
| scenarioId / scenarioVersion | 합성 시나리오의 명시적 식별자와 버전 |
| patientId | 공통 환자 ID. 이름·병실·배열 순서로 자동 매칭하지 않음 |
| encounterId | 새 통합 시나리오에서 명시하는 입원 식별자. 기존 데이터에 있었다고 소급 주장하지 않음 |
| shift.startsAt / endsAt | 시간대를 포함한 ISO 근무 구간 |
| reviewStartAt | 휴무 복귀 조회 시작점. 차팅 작성 시점과 별개 |
| recordVersion | 참조 기록 변경을 감지하는 버전. 원문 문자열을 저장 키에 노출하지 않음 |
| sourceRef | patient/encounter, 출처 모듈, 원본 ID 또는 path, 기록 시점, 출처 버전을 감싸는 연결 정보 |

인수인계 내부 API는 정확한 키 집합을 검증하므로 공통 필드를 기존 payload에 무조건 추가하지 않는다. 어댑터에서 기존 엔진 계약으로 변환하고 결과에 공통 출처 문맥을 붙인다.

차팅의 HH:mm에 임의로 오늘 날짜를 붙이지 않는다. 통합 시나리오에 날짜·시간대·각 원본 출처를 명시하고 기존 시각은 표시용 값으로 유지한다. 날짜가 없는 기존 데모는 독립 데모로 남는다.

기존 5명과 6명은 동일 환자 집합으로 취급하지 않는다. 첫 연결 검증은 명시적으로 작성한 공통 합성 시나리오 1명부터 수행하고, 환자 혼입 방지 검증에는 두 번째 별도 합성 환자를 사용한다. 최종 공통 환자 수는 구현 결과에 맞춰 기록한다.

## 5. 상태와 기록 반영

- 환자/입원별 초안, 추가 기록, 읽음, 수기 인계 메모를 각각 관리한다.
- 추천 표시와 채택은 차팅 편집 상태이며 원본 기록을 바꾸지 않는다.
- 명시적 기록 추가 후에만 통합 세션 기록 버전을 갱신한다. 추가 기록은 미서명 데모 상태로 남는다.
- SOAP 서술은 간호기록으로 연결한다. 이를 활력징후 수치, 투약 시행, 검사 결과, 처방 상태로 자동 역변환하지 않는다.
- 새 기록의 인수인계 입력 계약 수용 여부를 어댑터 테스트로 먼저 확인한다. 미지원 입력이면 기록은 보존하되 비교 반영 미지원 상태를 명시하고, 계산에 반영된 것처럼 표시하지 않는다. 서버 상태나 오더를 변경하지 않는다.
- 수용 가능한 새 기록의 인수인계 재조회가 성공한 뒤 검토 화면을 새 버전으로 전환한다. 실패 시 기존 성공 데이터와 작성한 신규 기록·사용자 입력을 보존하고 재시도를 제공한다. 검토 화면이 이전 recordVersion이라는 사실을 표시해 최신 결과로 오인시키지 않는다.
- 늦은 요청이 다른 환자·기록 버전의 화면을 덮지 못하도록 요청 문맥을 검증한다.
- 모듈 이동만으로 초안이 사라지지 않게 한다. 새로고침 보관 정책은 기존 차팅의 React 상태와 인수인계 sessionStorage 차이를 명시하고 통합 계약에서 별도 정한다.
- 여기서 모듈 이동은 같은 페이지의 업무 탐색을 뜻한다. 새 브라우저 탭 또는 전체 새로고침에서 차팅 초안·신규 기록 보존을 보장하지 않는다. 사용자 화면에 각 저장 범위를 구분해서 표시한다.
- 인수인계 읽음은 처치 완료·보고 완료·기록 서명을 뜻하지 않는다.
- 1차 공통 세션 계약 제안(정책 최종 승인 전): 기록과 차팅 초안은 페이지 세션의 공통 메모리 스토어에 환자·입원별로 보존하고, 전체 새로고침 시 소실되는 기존 차팅 경계를 유지한다. 인수인계 읽음/수기 메모는 기존 sessionStorage 정책을 유지하되 현재 시나리오·기록 버전·존재 항목으로 검증한다. 통합 저장 키는 scenarioVersion/patientId/encounterId를 포함한 문맥에서 파생한다. 기존 키는 검증 없는 자동 이관을 하지 않는다. 모듈은 이 공통 스토어를 구독하며 원본 fixture를 변경하지 않는다. 비교 대안은 모든 상태를 메모리로 통일하는 방식이며 더 단순하지만 기존 인수인계 새로고침 복원 정책이 바뀌므로 이번 안에서는 기존 경계 보존안을 권고한다.
- 새로고침으로 세션 신규 기록이 없어지면 그 기록에 의존한 읽음/메모를 현행 상태로 복원하지 않는다. 복원은 scenarioVersion + patientId + encounterId + source recordVersion의 일치와 현재 항목 존재를 모두 검증한다.

## 6. 기술적 충돌과 해소 조건

1. **서버 라우팅:** 인수인계 `vercel.json`은 `/api/*`를 Python `/api/index`로 rewrite한다. 차팅의 Node `/api/suggest`가 여기에 잡히지 않도록 별도 경로 처리와 회귀 검증이 필요하다.
2. **전역 CSS:** 두 앱의 shell과 전역 스타일을 동시에 그대로 복사하면 중복 환자 목록·중복 헤더·스타일 충돌이 생긴다. 공통 shell은 한 곳이 소유하고 모듈 스타일을 제한한다.
3. **환자 구조:** 차팅은 일반외과 수술/POD/status 필드를 요구한다. 인수인계 환자에 이 값을 지어 넣지 않는다. 공통 기본 필드와 모듈별 선택적 필드를 분리한다.
4. **차팅 결합도:** `ChartingWorkspace`는 합성 환자 import와 자체 환자 선택 상태를 가진다. 편집기 경계에 환자·기록·근거·콜백을 주입할 수 있게 분리해야 한다.
5. **하네스 범위:** 차팅 하네스의 단일 네트워크 경로 제한은 독립 차팅 앱에 적용된다. 통합 호스트의 네트워크 계약 변경은 통합 설계와 검증 명세에 명시해야 하며 조용히 완화하지 않는다.
6. **버전 기준:** 최신 로컬 코드, 원격 병합, 배포를 구분한다. 통합 전에 사용할 커밋을 확정한다.
7. **후속 반응 규칙의 기존 한계:** 차팅 담당은 현재 후속 확인이 응답 텍스트 존재 여부를 검사하고 투약 전후 시각·동일 투약 event를 검사하지 않는다고 확인했다. ISO 시각이나 sourceRef를 새로 연결하더라도 기존 규칙이 시간순 임상 검증을 수행한다고 설명하지 않는다. 이 규칙의 강화는 별도 요구사항과 검증 범위다.
8. **진행 중 차팅 검증:** 차팅 담당의 `docs/verification/2026-09-23-synthetic-audit.md`, `src/domain/syntheticAudit.test.ts`, `src/features/charting/ChartingWorkspace.audit.test.tsx`는 진행 중 초안이다. 통합 베이스의 완료 산출물로 가져오지 않으며 담당 작업을 보존한다.
