# 휴무 복귀 인계 설계

- 상태: 사용자 검토용 설계
- 목표 버전: `0.8.0`
- 기준 제품: Nurse Handover Assistant `0.7.2`
- 적용 하네스: `1.2.0`
- 데이터 범위: 가상 일반 성인병동 기록

## 1. 문제 정의

현재 제품은 선택 환자의 직전 기록과 현재 기록을 비교하여 한 교대 구간의 변화를 보여준다. 그러나 인계를 받는 간호사가 며칠간 근무하지 않았다면 시작 시점과 현재 시점만 비교해서는 휴무 중 발생했다가 종료된 사건, 여러 번 변경된 투약, 활력징후의 중간 변동을 복원할 수 없다.

`휴무 복귀 인계`는 간호사의 마지막 근무 이후 현재까지 존재하는 모든 가상 snapshot을 인접 시점끼리 비교하고, 그 결과를 날짜별 사건과 현재 확인 항목으로 재구성한다. 원본 기록에 없는 사실이나 임상적 해결 여부는 추론하지 않는다.

## 2. 목표

1. 1일 이상 근무 공백 뒤 복귀한 간호사가 휴무 중 변화 흐름을 빠르게 파악한다.
2. 시작과 종료 시점이 같은 항목이라도 중간에 발생한 사건을 누락하지 않는다.
3. 모든 요약 문장을 특정 변화 사건과 두 원본 snapshot으로 추적할 수 있다.
4. 현재의 직전 교대 비교 기능과 응답 계약을 깨지 않는다.
5. API 키가 없거나 AI 문장화가 실패해도 규칙 기반 복귀 인계를 완성한다.
6. Vercel의 무상태 제약 안에서 번들 가상 데이터만으로 전체 시연이 가능하다.

## 3. 비목표

- 실제 근무표, 사용자 인증, 병원 EMR 또는 실제 환자정보 연동
- 간호 문제의 해결, 활력징후의 정상·비정상, 보고 필요성을 자동 판단하는 기능
- 실제 환자에게 기록하거나 오더를 변경하는 기능
- 여러 사용자와 기기 사이의 검토 상태 공유
- 퇴원·전동이 완료되어 현재 담당 목록에 없는 환자의 병상 이력 추적
- 실제 기관별 중요도·에스컬레이션 규칙 확정

## 4. 승인된 접근

### 4.1 인접 snapshot 타임라인

기간의 첫 기록과 현재 기록만 비교하지 않는다. 기준 snapshot부터 현재 snapshot까지 정렬한 후 `(R0, R1)`, `(R1, R2)`, … `(Rn-1, Rn)`을 기존 deterministic 비교 엔진으로 각각 비교한다.

이 방식은 기존의 검증된 진단·투약·활력징후·간호 메모 차이 검출을 재사용하면서 다음 사건을 보존한다.

- 휴무 중 추가되었다가 현재는 사라진 투약
- 여러 교대에 걸쳐 두 번 이상 변경된 투약 빈도
- 상승 후 다시 내려간 활력징후 값
- 중간 snapshot에만 존재하는 진단 또는 메모 변화

### 4.2 별도 기간 비교 계약

기존 `/api/handover/compare`는 두 기록 비교 전용으로 유지한다. 복귀 인계는 새 `/api/handover/period-compare`를 사용한다. 기존 계약을 확장하지 않는 이유는 현재 교대 비교의 테스트·세션·편집 경계를 보존하고, 다중 시점 오류가 기존 화면에 전파되지 않게 하기 위해서다.

### 4.3 수동 마지막 근무 선택

MVP에는 근무표가 없으므로 사용자가 가상 기록에 존재하는 마지막 근무 종료 시점을 선택한다. `휴무 복귀` 모드의 기본 시나리오는 `3일 전 마지막 근무`이며, 선택지는 해당 환자 타임라인에서 실제 비교 가능한 시각만 제공한다.

## 5. 용어와 시간 경계

| 용어 | 정의 |
|---|---|
| 복귀 기준 시각 | 사용자가 선택한 마지막 근무 종료 시각 |
| 기준 snapshot | 복귀 기준 시각과 같거나 그 이전인 snapshot 중 가장 최신 기록 |
| 현재 snapshot | 선택 환자 타임라인의 가장 최신 기록 |
| 포함 snapshot | 기준 snapshot부터 현재 snapshot까지의 정렬된 기록 |
| 기간 사건 | 인접 snapshot 비교에서 검출된 하나의 변화 항목 |
| 현재 반영 | 진단·투약의 마지막 변화 결과가 현재 snapshot에 남아 있는 상태 |
| 기간 중 종료 | 진단·투약이 휴무 중 추가되었으나 현재 snapshot에는 남아 있지 않은 상태 |
| 추세 | 활력징후가 기간 중 한 번 이상 변경된 값의 시간순 목록 |
| 기록 사건 | 간호 메모의 추가·삭제 이력. 해결 여부를 뜻하지 않는다. |

모든 시각은 ISO 8601 offset 포함 문자열로 전달하고 비교한다. 데모 데이터는 `+09:00`을 사용한다. 기준 시각과 같은 snapshot이 없으면 가장 가까운 이전 snapshot을 기준으로 삼고 실제 기준 기록 시각을 화면에 함께 표시한다. snapshot 비교는 사건의 실제 발생 시각을 증명하지 않으므로 `occurredAt` 대신 뒤쪽 snapshot의 기록 시각인 `detectedAt`을 사용한다.

## 6. 데이터 설계

### 6.1 데모 데이터

현재 데이터는 환자별 과거 2개와 현재 1개, 약 10~15시간 범위뿐이다. 복귀 인계 시연을 위해 환자 5명 각각에 66시간 이상, 정확히 8개 시점의 가상 snapshot을 제공한다. 전체 기록은 40개이며 모든 환자가 동일한 snapshot 수를 가진다.

새 타임라인 fixture는 `data/timelines/P001.json`부터 `P005.json`에 둔다. 각 파일은 다음 구조를 사용한다.

```json
{
  "patientId": "P001",
  "defaultReturnStartAt": "2026-06-29T15:00:00+09:00",
  "snapshots": [],
  "coverageGaps": []
}
```

`snapshots`의 마지막 기록은 기존 `data/patients/Pxxx.json`과 의미상 동일해야 한다. 자동 테스트가 환자 ID, 최신 시각과 전체 임상 필드의 동일성을 검사해 두 데이터 계열의 드리프트를 차단한다.

각 환자의 3일 시나리오는 최소한 다음 경우를 포함한다.

- 현재도 유지되는 새 진단 또는 투약
- 휴무 중 시작 후 현재 전에 종료된 투약
- 동일 투약의 두 번 이상 빈도 또는 경로 변경
- 활력징후의 두 번 이상 변동
- 지속되는 간호 메모와 현재 목록에서 사라진 메모
- 한 환자의 명시적 데이터 공백

`coverageGaps`는 시간 차이만으로 누락을 추측하지 않기 위한 명시적 메타데이터다. 각 항목은 `from`, `to`, `code`를 가지며 기간과 겹치면 전체 결과를 `partial`로 만든다.

### 6.2 브라우저 데이터 경계

`src/lib/demo-timelines.ts`가 JSON을 정적 import하고 읽기 전용 `DemoRecordTimeline`으로 노출한다. 실제 파일 쓰기나 서버 영속 저장은 하지 않는다. 원본 기록 편집 sandbox는 기존처럼 브라우저 세션 안에서만 동작하며, 편집된 현재 기록을 기간 타임라인의 마지막 snapshot 대신 사용할 수 있다.

## 7. 핵심 로직

새 `services/handover_period_service.py`가 기간 비교만 담당한다. 기존 `build_handover_comparison(previous, current)`은 수정 범위를 최소화하고 그대로 호출한다.

처리 순서는 다음과 같다.

1. 입력이 목록인지 검증한다.
2. 모든 snapshot의 환자 식별자가 같은지 확인한다.
3. `updated_at`을 offset-aware ISO 시각으로 파싱한다.
4. 입력 순서와 무관하게 시각순으로 안정 정렬한다.
5. 중복 시각과 유효하지 않은 기록을 검출한다.
6. 복귀 기준에 해당하는 기준 snapshot을 선택한다.
7. 기준부터 현재까지 인접 snapshot을 pairwise 비교한다.
8. 각 `HandoverChange`를 고유한 `PeriodEvent`로 감싼다.
9. 진단·투약 생명주기, 활력징후 추세, 메모 기록 사건을 규칙 기반으로 묶는다.
10. 중요도와 시각을 기준으로 현재 확인 그룹과 날짜별 타임라인을 만든다.
11. 요약의 모든 `evidenceIds`가 실제 기간 사건을 가리키는지 검증한다.

### 7.1 사건 ID

기존 변화 ID는 서로 다른 pair에서 반복될 수 있으므로 그대로 전역 ID로 쓰지 않는다. 기간 사건 ID는 환자 ID, 현재 snapshot 시각과 기존 변화 ID를 정규화하여 생성한다. 같은 입력은 항상 같은 ID를 만들고, 다른 시점의 동일 필드 변화는 서로 다른 ID를 가져야 한다. ID에는 환자 이름이나 원문 메모를 포함하지 않는다.

기간 사건과 검토 그룹의 최소 계약은 다음과 같다.

```text
PeriodEvent
├─ id
├─ detectedAt
├─ interval
│  ├─ previousRecordedAt
│  └─ currentRecordedAt
├─ classification: current | period_only | trend | record_event
└─ change: HandoverChange

PeriodReviewItem
├─ id
├─ category
├─ label
├─ classification
└─ eventIds[]
```

`reviewGroups.current`, `periodOnly`, `trends`, `recordEvents`는 `PeriodReviewItem[]`이며 각 항목은 하나 이상의 실제 기간 사건 ID만 참조한다. 값과 근거의 단일 기준은 `events[].change`다.

### 7.2 생명주기 규칙

- 진단과 투약은 구조화 필드이므로 `현재 반영` 또는 `기간 중 종료`로 분류할 수 있다.
- 기준 snapshot과 현재 snapshot의 상태가 다르면 제거·중단을 포함해 `현재 반영`으로 분류한다.
- 기준과 현재 상태는 같지만 중간에 추가·제거 또는 변경·복귀가 있었다면 `기간 중 종료`로 분류한다.
- 추가 후 변경된 투약은 하나의 현재 항목에 변화 이력을 연결하되 모든 중간 사건을 보존한다.
- 추가 후 제거된 진단·투약은 `기간 중 종료`라고만 표현한다. 치료 완료 또는 문제 해결이라고 표현하지 않는다.
- 활력징후는 시간순 `이전값 → 중간값 → 현재값`으로 묶는다. 정상화·악화 같은 임상 평가는 하지 않는다.
- 간호 메모는 추가·삭제 사건을 시간순으로 표시한다. 삭제를 문제 해결로 해석하지 않는다.

### 7.3 우선순위

MVP는 기존 비교 엔진의 `high`, `medium`, `low`를 그대로 사용한다. 새 임상 threshold나 병동별 보고 규칙을 추가하지 않는다. 현재 확인 목록은 `high`를 먼저, 그다음 최신 시각, 카테고리, 사건 ID 순으로 안정 정렬한다.

## 8. API 계약

### 8.1 요청

```json
{
  "reviewStartAt": "2026-06-29T15:00:00+09:00",
  "records": [],
  "coverageGaps": [],
  "summaryMode": "ai"
}
```

- `records`: 최소 1개 이상의 동일 환자 snapshot
- `reviewStartAt`: offset을 포함한 ISO 8601 시각
- `coverageGaps`: 데모 데이터가 명시한 누락 구간
- `summaryMode`: `deterministic` 또는 `ai`

### 8.2 응답

```text
HandoverPeriodResponse
├─ patient
├─ period
│  ├─ requestedStartAt
│  ├─ baselineRecordedAt
│  ├─ currentRecordedAt
│  ├─ snapshotCount
│  ├─ eventCount
│  └─ status: ready | no_baseline | no_events | partial
├─ dataWarnings[]
├─ events[]
├─ reviewGroups
│  ├─ current[]
│  ├─ periodOnly[]
│  ├─ trends[]
│  └─ recordEvents[]
└─ summary
   ├─ mode
   ├─ sections
   ├─ evidenceIds[]
   └─ warnings[]
```

`events`가 기간 내 전체 사실의 단일 기준이다. `reviewGroups`와 `summary`는 사건 ID만 참조하며 원본 사실을 복제해 별도 진실 원본을 만들지 않는다.

### 8.3 상태와 오류

| 상태 | 조건 | 화면 처리 |
|---|---|---|
| `ready` | 기준과 현재가 있고 사건이 존재하며 알려진 공백 없음 | 전체 복귀 인계 표시 |
| `no_baseline` | 복귀 기준 이전 snapshot이 없음 | 기준 기록 부재를 표시하고, 기준 이후 snapshot 사이에서 확인 가능한 사건과 현재 기록만 제공 |
| `no_events` | 유효한 기간이나 변화 없음 | 해당 기간 변화 없음 표시 |
| `partial` | 명시적 공백, 불완전 필드 또는 일부 pair 경고 | 부분 요약 경고와 확인 가능한 사건만 표시 |

환자 불일치, 유효하지 않은 시각, 빈 현재 기록은 HTTP 422로 거절한다. OpenAI 키 부재, timeout, provider 오류, 잘못된 구조화 출력은 HTTP 오류로 바꾸지 않고 deterministic 요약과 경고로 응답한다.

## 9. 요약 계약

SBAR 틀은 기존 화면과 일관되게 유지한다.

- Situation: 환자, 병실, 실제 기준 snapshot 시각, 현재 시각, 기간 사건 수
- Background: 기간 중 진단·투약 사건과 현재 반영 여부
- Assessment: 활력징후 추세와 간호 메모 기록 사건
- Recommendation: `간호사가 확인할 후속 항목을 입력하세요.` 기본 문구

LLM은 deterministic 사건과 그룹을 문장화할 수 있지만 다음을 변경할 수 없다.

- 사건 수와 ID
- 이전·현재·중간 값
- 검출 기록 시각
- 현재 반영 또는 기간 중 종료 분류
- 우선순위
- 데이터 공백과 경고

LLM 출력에 사건 누락, 알 수 없는 ID, 값 변경, 해결·악화 같은 추가 판단이 있으면 전체 AI 결과를 버리고 규칙 요약을 사용한다.

## 10. 화면 설계

### 10.1 모드 전환

현재 중앙 상단에 `직전 교대 | 휴무 복귀` 두 모드를 둔다. 초기값은 기존 기능을 보존하기 위해 `직전 교대`다. `휴무 복귀`를 선택하면 `마지막 근무` 선택기가 나타나며 기본값은 3일 전 시나리오다.

환자를 변경하면 해당 환자의 사용 가능한 마지막 근무 선택지와 기간 결과를 함께 갱신한다. 요청 중에는 기존과 동일하게 환자 전환은 허용하되, 이전 환자의 늦은 응답이 현재 환자 결과를 덮어쓰지 못하게 요청 세대 가드를 적용한다.

### 10.2 환자 컨텍스트

`이번 근무 변화`는 모드에 따라 `3일 복귀 인계`처럼 바뀐다. 비교 구간에는 사용자가 요청한 시각이 아니라 실제 기준 snapshot 시각과 현재 시각을 표시하고, 둘이 다르면 `선택 시각 이전의 가장 가까운 기록 기준` 안내를 표시한다.

### 10.3 중앙 작업 영역

중앙은 다음 순서로 구성한다.

1. `현재 확인` — 현재 반영된 high 우선순위 사건
2. `기간 중 종료` — 휴무 중 발생했다가 현재 전에 종료된 진단·투약
3. `활력징후 추세` — 항목별 시간순 값 변화
4. `전체 타임라인` — 날짜와 시각으로 그룹화한 모든 사건

각 행은 검출 기록 시각, 카테고리, 변화 표현, 현재 반영 상태와 근거 열기 기능을 가진다. 실제 발생 시각으로 표현하지 않으며 `기간 중 종료`는 해결 또는 완료라는 표현을 사용하지 않는다.

### 10.4 인계 검토 레일

우측 레일 제목은 `복귀 인계 검토`로 바뀌며 상단에 다음 수치를 표시한다.

- 기간 사건 총수
- 현재 확인 수
- 기간 중 종료 수
- 근거 포함률

SBAR 섹션과 원본 확인·검토 완료 흐름은 기존 계약을 재사용한다. 기간이나 마지막 근무를 변경하면 이전 검토 완료·선택 근거·수기 Recommendation을 새 결과에 재사용하지 않고 새 검토 세션을 만든다.

### 10.5 원본 기록 이동

근거를 선택하면 `원본 기록` 모드에서 해당 사건의 정확한 이전·현재 snapshot을 나란히 연다. 현재의 편집 sandbox는 최신 현재 기록에만 적용한다. 과거 snapshot은 모두 읽기 전용이다.

### 10.6 반응형

- 1280px 이상: 환자 레일·중앙·검토 레일의 3열 유지
- 960~1279px: 기존 태블릿 레일 폭과 중앙 overflow 계약 유지
- 959px 이하: 중앙 모드와 우측 검토를 탭 또는 순차 영역으로 제공
- 390px: 사건 행을 `시각/상태`, `변화`, `근거` 순서의 단일 열로 쌓고 수평 overflow를 만들지 않음
- 1600px 이상: `0.7.2`의 와이드 글자 크기와 304px/400px 레일 계약 유지

## 11. 상태 관리

기간 결과 캐시는 `patientId + reviewStartAt + currentRecordFingerprint`를 키로 사용한다. `currentRecordFingerprint`는 최신 현재 기록의 정규화 JSON으로 만든 결정적 hash이며 원문 값을 캐시 키 문자열에 노출하지 않는다. 다음 동작은 새 비교 성공 후에만 결과를 교체한다.

- 마지막 근무 변경
- 환자 변경 후 복귀 모드 진입
- 최신 현재 기록 편집 후 재비교
- 데모 초기화

실패 시 기존 성공 결과와 사용자 입력을 보존하고 오류 안내만 갱신한다. 현재 기록 편집이 성공하면 기간 타임라인의 마지막 snapshot만 새 기록으로 교체하여 재계산한다. `sessionStorage`에는 기존과 동일하게 가상 현재 기록 draft만 저장하며 기간 결과 전체를 영속 저장하지 않는다.

## 12. 접근성

- 모드 전환은 `tablist`와 `tab` 키보드 계약을 사용한다.
- 마지막 근무 선택기는 명시적 label과 실제 기준 시각 설명을 가진다.
- 날짜별 타임라인 제목은 heading 구조를 사용한다.
- 색상만으로 현재 반영·기간 중 종료·부분 결과를 구분하지 않는다.
- 근거 이동 뒤 대상 사건 또는 원본 기록 제목으로 focus를 이동한다.
- 로딩·부분 결과·fallback은 `aria-live`를 과도하게 중복하지 않고 한 상태 영역에서 알린다.

## 13. 테스트 전략

### 13.1 핵심 로직

- 3개 이상 snapshot에서 모든 인접 변화가 한 번씩 사건화됨
- 추가 후 제거된 투약이 시작·종료 두 사건과 `기간 중 종료` 그룹을 가짐
- 동일 투약의 연속 변경이 중간 값을 보존함
- 활력징후 상승 후 하강이 최종 endpoint 비교에 사라지지 않음
- 메모 삭제가 해결 상태로 분류되지 않음
- 서로 다른 환자, 중복 시각, invalid ISO, 불완전 필드와 역순 입력의 안정 정렬 처리
- 기준 시각 이전의 가장 가까운 snapshot 선택
- 명시적 coverage gap이 `partial`을 생성함
- 사건 ID의 결정성·유일성과 안정 정렬

### 13.2 API와 AI fallback

- 새 endpoint의 정상·no baseline·no events·partial·422 계약
- 입력 fixture와 파일이 호출 전후 동일함
- API 키 없음, timeout, provider 실패, malformed/unsupported AI 출력에서 규칙 요약 유지
- AI 문장화가 모든 사건 ID와 사실을 보존하는지 검증

### 13.3 프런트엔드

- 직전 교대 모드의 기존 동작과 테스트가 그대로 통과함
- 모드·환자·마지막 근무 전환의 요청 경쟁 방지
- 기간 변경 시 검토 세션과 Recommendation 초기화
- 현재 기록 편집 성공·실패의 트랜잭션 경계
- 사건 근거에서 정확한 과거 snapshot 쌍으로 이동
- partial·no baseline·no events·fallback 화면

### 13.4 E2E와 시각 검증

- P001 3일 복귀 시나리오에서 현재 반영·기간 중 종료·추세·전체 타임라인 확인
- 모든 SBAR 근거가 존재하는 사건과 원본 기록으로 이동
- 2544·1440·1279·1024·960·390px에서 수평 overflow와 가림 없음
- Production에서 루트·health·기간 API, 변화 수와 근거 수 smoke 검증

## 14. 수용 기준

1. P001의 3일 시나리오에 endpoint 간 비교로는 보이지 않는 최소 1개의 기간 중 사건이 표시된다.
2. 모든 인접 비교 변화가 정확히 하나의 기간 사건에 포함된다.
3. summary가 참조하는 사건 ID의 포함률이 100%다.
4. 투약·진단의 현재 반영/기간 중 종료가 fixture 기대값과 100% 일치한다.
5. 활력징후와 메모에 임상적 해결·악화 추론이 생성되지 않는다.
6. 데이터 공백이 있는 환자는 `partial`과 공백 구간을 표시한다.
7. 기존 직전 교대 비교의 Python·Vitest·Playwright 계약이 모두 유지된다.
8. 390px부터 2544px까지 핵심 흐름에 수평 overflow가 없다.
9. OpenAI 호출 불가 상태에서도 동일 사건·근거를 가진 규칙 요약이 제공된다.
10. 실제 환자정보, API 키, 영속 데이터가 저장소·클라이언트·로그에 추가되지 않는다.

## 15. 구현 경계와 순서

1. 가상 타임라인 fixture와 TypeScript/Python 기간 계약
2. `handover_period_service`와 단위 테스트
3. 기간 API와 fallback 검증
4. 브라우저 adapter, 요청 세대·세션 경계
5. 모드 선택, 기간 사건 중앙 화면, 복귀 검토 레일
6. 원본 snapshot 근거 이동과 최신 기록 편집 재비교
7. 반응형·접근성·E2E·Production 검증
8. 문서, 작업 로그, `0.8.0` 버전과 Vercel 배포

각 큰 단계는 담당 Luna Max 에이전트의 구현·자체 검증, 감독 코드 리뷰·테스트·화면 확인, 독립 리뷰를 통과한 후 다음 단계로 진행한다.

## 16. 결정 근거

| 결정 | 근거 | 감수하는 비용 |
|---|---|---|
| 인접 snapshot 비교 | 중간 발생 후 종료된 사건을 보존하고 기존 검증 엔진을 재사용 | snapshot 수에 비례해 비교 횟수 증가 |
| 새 기간 endpoint | 기존 2시점 API·편집·검토 계약의 회귀 위험 차단 | API 타입과 adapter 추가 |
| 수동 마지막 근무 선택 | 근무표·인증 없이도 실제 사용 흐름을 시연 | 자동 개인화는 운영 연동까지 미지원 |
| 명시적 coverage gap | 임의 시간 간격으로 누락을 오판하지 않음 | fixture 메타데이터 관리 필요 |
| 현재 반영/기간 중 종료 표현 | 원본 구조로 확인 가능한 상태만 전달 | 임상적 해결·중요성 표현은 제한됨 |
| 기존 우선순위 재사용 | 새 임상 threshold를 임의로 만들지 않음 | 기관별 고도화 전까지 정밀 우선순위 제한 |
| 정적 가상 데이터 | Vercel 무상태 배포와 포트폴리오 재현성 보장 | 실제 근무표·공유 상태 미지원 |

## 17. 후속 운영 확장

포트폴리오 MVP 이후에만 다음을 별도 설계한다.

- 사용자 인증과 근무표에서 복귀 기준 자동 계산
- EMR event feed 또는 audit log 기반 기록 수집
- 기관 승인 중요도·보고 규칙
- 사용자별 마지막 확인 시각과 다중 기기 공유
- 병동 이동·입퇴원·담당 환자 변경 이력

이 항목들은 현재 `0.8.0` 구현 범위와 데이터 계약에 포함하지 않는다.
