# Nurse Handover Assistant - Step 3: 질의형 조회 MVP 설계

## 목적

이 단계의 목표는 Step 2에서 구축한 `입력 -> 저장 -> 인수인계` 흐름 위에,
자연어 기반 `질의 조회` 기능을 추가하는 것이다.

이 단계에서는 다음을 구현 대상으로 본다.

1. `질의 조회` 탭 추가
2. 환자 최신본과 history snapshot을 활용한 검색 기능 구현
3. 지원 질의 / 결과 없음 / 미지원 항목을 구분하는 응답 구조 정의
4. 질의형 시연에 적합한 샘플 데이터 확장

## 왜 Step 3로 분리하는가

Step 2의 핵심은 Streamlit 기반 입력/저장/인수인계 MVP 완성이다.
질의형 조회는 그 위에 올라가는 별도의 사용자 가치이므로,
설계와 구현 범위를 분리하는 것이 문서상 더 명확하다.

Step 3는 다음 질문에 답하는 기능이다.

- 특정 환자의 최근 변동사항은 무엇인가
- 어제 발열이 있었던 환자는 누구인가
- 특정 약물/메모/진단 키워드에 해당하는 환자는 누구인가

## 사용자 흐름

1. 사용자가 `질의 조회` 탭으로 이동한다
2. 자연어 질문을 입력한다
3. 시스템이 질문을 규칙 기반으로 해석한다
4. 지원되는 질의면 최신본과 history snapshot을 검색한다
5. 결과를 표 형태 또는 텍스트 형태로 보여준다
6. 현재 데이터 구조에 없는 항목이면 미지원 메시지를 표시한다

## 화면 구조

Step 3에서는 Step 2의 3개 탭에 아래 탭을 추가한다.

4. `질의 조회` 탭

구성:

- 질문 입력창
- 예시 질문 표시
- 조회 버튼
- 결과 테이블
- 미지원 항목 안내 메시지

예시 질문:

- `P001 환자 변동사항 뭐야?`
- `어제 열났던 환자 찾아줘`
- `와파린 투약 중인 환자 보여줘`
- `통증 메모 있는 환자 찾아줘`

## 지원 질의 범위

MVP에서는 현재 스키마에 존재하는 필드만 검색 대상으로 본다.

지원 대상:

- 환자 ID 기반 변동사항 조회
- 체온 기록 기반 발열 환자 조회
- medications 기반 약물 키워드 조회
- notes 기반 메모 키워드 조회
- diagnosis 기반 진단 키워드 조회

미지원 예시:

- `CT 촬영한 환자 찾아줘`
- `MRI 오더 난 환자 보여줘`
- `검사 결과 abnormal 환자 찾아줘`

현재 데이터 구조에 `orders`, `imaging`, `labs` 필드가 없기 때문에,
위 질의는 `데이터베이스에 조회되지 않는 항목입니다`로 응답한다.

## 질의 조회 흐름

`질의 조회` 탭에서 질문을 입력하면 아래 순서로 처리한다.

1. 질문 문자열 입력
2. 환자 ID 질의 / 어제 발열 질의 / 키워드 환자 질의 여부 판별
3. 데이터 구조에 없는 항목인지 먼저 확인
4. 지원되는 질의면 최신본과 history snapshot을 직접 검색
5. 조회 결과를 표 형태로 렌더링
6. 미지원 질의면 안내 메시지를 표시

주의:

- MVP에서는 LLM이 아니라 deterministic rule 기반으로 질문을 해석한다
- `어제`는 시스템 오늘 날짜가 아니라 데모 데이터의 최신 기록 시각을 기준으로 계산한다
- 질의형 검색의 정확한 범위는 현재 스키마에 존재하는 필드로만 제한한다

## 모듈 설계

### services/query_service.py

역할:

- 자연어 질문을 MVP 범위의 규칙 기반 질의로 해석
- 환자 최신본 및 history snapshot 검색
- 조회 성공 / 결과 없음 / 미지원 항목을 구분해 응답

핵심 함수:

- `run_query(question)`

### services/storage_service.py

Step 3에서 history 기반 질의를 위해 아래 보조 함수를 추가한다.

- `load_patient_history(patient_id)`
- `load_patient_timeline(patient_id)`

### app.py

Step 3에서 아래를 추가한다.

- `질의 조회` 탭 렌더링
- 예시 질문 표시
- 질의 결과 상태 메시지 및 테이블 표시

## 샘플 데이터 설계 원칙

질의형 조회 시연을 위해 각 환자는 `현재본 1개 + history 2개` 구조를 가진다.

환자별 대표 이벤트는 아래와 같이 분산한다.

- `P001`: 발열 및 혈압 상승, 해열제 추가
- `P002`: 폐렴 환자의 산소 요구량 감소와 해열 경과
- `P003`: 심부전 환자의 이뇨제 증량과 부정맥 진단 추가
- `P004`: 수술 후 통증 감소와 보행 시작
- `P005`: 당뇨발 환자의 항생제 추가와 체온 안정화

이 구조로 아래 시연이 가능하다.

- 특정 환자 최근 변동사항 조회
- 어제 발열 환자 조회
- 약물명 기반 환자 검색
- 메모 키워드 기반 환자 검색

## 다음 단계 확장 포인트

Step 3 이후에는 아래 순서로 확장할 수 있다.

1. LLM 기반 질의 parser 추가
2. 질의 의도 분류를 JSON schema로 구조화
3. 병실 필터, 시간대 필터 추가
4. orders / imaging / labs 스키마 확장
5. OpenAI 기반 인수인계 문장화와 질의 응답 통합

## 후속 MVP 개발 계획

Step 3 이후의 후속 MVP는 OpenAI API를 검색 엔진 자체로 쓰기보다,
기존 deterministic 로직 위에 `표현`과 `질문 해석` 계층을 추가하는 방향으로 진행한다.

우선순위는 아래와 같다.

### 1. 인수인계 문장화

목표:

- 기존 `detect_changes()` 결과를 더 읽기 쉬운 한국어 인수인계 문장으로 변환

원칙:

- 변화 검출은 기존 코드가 담당한다
- LLM은 문장 재작성만 담당한다
- 환자 원문 전체가 아니라 `changes` 중심의 축약 payload만 전달한다
- API 실패 시 기존 rule-based bullet 결과로 fallback 한다

예상 구현:

- `services/openai_service.py`
- `generate_ai_handover(changes, patient_context)`

### 2. 질의형 질문 parser

목표:

- 현재의 규칙 기반 질문 해석을 더 자연스러운 자유 질문까지 확장

원칙:

- LLM은 질문을 `intent + filters` 구조로 파싱만 한다
- 실제 환자 검색과 판정은 기존 Python 코드가 담당한다
- 구조화 결과는 JSON schema 기반으로 검증한다

예상 구현:

- `parse_query_to_filters(question, supported_schema)`
- 예: `어제 열났던 환자 중 산소 쓰는 사람` -> 발열 + 투약/산소 조건 필터

### 3. 검색 결과 설명 생성

목표:

- 조회 결과가 여러 명일 때 테이블만 보여주지 않고 요약 문장을 함께 제공

원칙:

- 모델이 검색 결과를 새로 찾는 것이 아니라,
  이미 검색된 결과를 설명 형태로 압축한다
- 수치와 약물명은 원본 그대로 유지한다

예상 구현:

- `summarize_query_results(question, results)`

### 4. 미지원 질의 응답 고도화

목표:

- 현재는 단순히 `조회되지 않는 항목`만 보여주지만,
  이후에는 사용 가능한 대체 질의를 함께 안내

예:

- `CT 촬영한 환자` -> `현재는 CT/검사 오더 필드가 없어 조회할 수 없습니다. 대신 진단명, 투약, 메모, 활력징후 기반 조회는 가능합니다.`

## API 키 관리 계획

OpenAI API를 붙일 때 키 관리는 아래 원칙을 따른다.

### 로컬 개발

- `.env` 파일에 `OPENAI_API_KEY` 저장
- 앱 시작 시 `python-dotenv` 또는 명시적 환경 변수 로딩으로 사용

### Streamlit Community Cloud

- GitHub에 키를 올리지 않는다
- Streamlit Cloud의 `Secrets`에 `OPENAI_API_KEY` 저장
- 앱에서는 `st.secrets["OPENAI_API_KEY"]`로 읽는다

### 공통 원칙

- API 키는 코드에 하드코딩하지 않는다
- `.env`는 git에 포함하지 않는다
- 키가 없으면 AI 기능을 비활성화하고 기존 deterministic 기능만 유지한다

## 설계 원칙

후속 MVP에서도 아래 원칙을 유지한다.

1. 사실 검색과 변화 검출은 코드가 담당한다
2. LLM은 문장화, 질문 해석, 결과 요약에만 사용한다
3. 없는 데이터를 LLM이 추정해서 답하지 않도록 제한한다
4. AI 기능은 항상 fallback 가능한 선택 계층으로 유지한다

## 구현 시 주의점

1. 질의형 조회도 MVP 단계에서는 스키마 기반 deterministic 검색으로 제한하는 것이 안전하다
2. 없는 데이터를 추정해서 응답하면 안 된다
3. demo 질의가 잘 동작하도록 history 시각은 일관되게 설계해야 한다
4. 미지원 질의와 결과 없음은 서로 다른 상태로 구분해야 한다

이 문서는 Streamlit 기반 Nurse Handover Assistant의 질의형 조회 MVP 설계 문서이다.
